# Harness ablation, 2026-10-21 (first run)

The first measurement of what one harness mechanism adds, with the model and the cases held fixed.

- Model: GPT-6 Luna. Cases: `research/mcp-facts`, `3d/fire-hydrant`. Two repeats each.
- Configurations: `baseline` (as shipped), `no-code-mode` (the `run_script` tool removed), `compact-early` (compaction at 60k tokens).
- Harness: commit 5918ee1, native Windows 11.

| Config | Pass | 95% CI | Median cost (min-max) | Δ cost vs baseline | Median time |
|---|---|---|---|---|---|
| baseline | 4/4 | 51%-100% | $0.035 ($0.021-$0.047) | - | 8 min |
| no-code-mode | 4/4 | 51%-100% | $0.028 ($0.018-$0.041) | -$0.007 | 8 min |
| compact-early | not scored | | | | |

**What it shows:** on these two cases code mode bought nothing - both configurations
passed every hidden check, and without `run_script` the runs were slightly cheaper
(fewer calls). That differs from the phase 5 measurement, where code mode halved the
cost of data-heavy research; these cases move little data through tool results. With
2 repeats per cell the intervals are wide (51%-100%), so this is a direction, not a
verdict: code mode pays where intermediate results are large, and is overhead where
they are not.

**Not scored:** all four `compact-early` runs stopped when the OpenAI account ran
out of credits ("You have no credits remaining"). The eval runner now tells provider
failures (credits, keys, outages) apart from the agent failing: such runs are listed
as "not scored" and kept out of the pass rates (it first counted them as failures,
which would have read as "early compaction breaks the agent").

The same run found a crash in the `web-console` gate when it was asked for by name in
a workspace with no page; it now fails with a reason.

Next: the same configurations with 3+ repeats on more cases (a data-heavy research
case for code mode, the long task for compaction) once the account has credits.
