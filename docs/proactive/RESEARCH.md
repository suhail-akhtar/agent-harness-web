# Build proactive agents around a review queue

Yes, build it, but not as an assistant that is always on and decides for itself when to interrupt. Build a governed layer on the core: user-authored automations, cheap detection that runs without a model, and an agent inbox that the person owns. A proactive agent watches a schedule or an event stream, infers that something needs doing, and decides **whether, when and how** to act, which includes deciding to stay silent. The research and product record agrees on one point. Proactive help pays off when it catches the right moment: an error just raised, a scheduled chore, a change worth knowing about. It turns net-negative when it becomes frequent, noisy or autonomous in shared spaces. In the best controlled study, preference fell from **90% to 47%** once suggestions came more often ([Chen et al., CHI 2025](https://arxiv.org/html/2410.04596v2)). Even the best models raise **false alarms about half the time** ([Lu et al.](https://arxiv.org/html/2410.12361v3)). OpenAI reportedly folded its agent-chosen Pulse feed back into user-authored scheduled tasks in June 2026 ([Digit](https://www.digit.in/news/general/openai-is-retiring-chatgpt-pulse-and-replacing-it-with-scheduled-tasks-here-is-why.html)). Our harness already owns most of the hard parts: a lease-safe cron scheduler, secret-URL triggers, an initiative model with three levels, a taint guard, sandboxes, cost caps, an approvals inbox, and a working model-free watch loop in the Operations solution. What it lacks is the part users actually see. Run outcomes are recorded only as "started", findings go nowhere visible, and unattended runs refuse anything that would need a person instead of parking it for review. The inventory also found **concrete bugs**. The desktop "New schedule" form looks unable to create a schedule at all. Scheduled runs skip the daily spend check. Info notices from a scheduled agent never reach the person. The recommendation is to fix those first, then add run records, an agent inbox with a "park, don't deny" mode, a core watch primitive, and finally an initiative policy that learns from feedback. Agent-chosen, in-editor proactivity comes last, and only if the data from the earlier phases supports it.

## Proactivity means choosing to act, ask or stay silent without being asked

The literature separates proactivity from autonomy. Autonomy is how much an agent can do unattended. Proactivity is **initiative**: deciding what matters and surfacing it unasked. Bui and Evangelopoulos argue that coding agents "need proactivity, not just autonomy". They propose three levels, **Reactive → Scheduled → Situation-Aware**, and an "insight policy" that decides what matters next, what evidence supports it, whether to surface it, and how to adapt after feedback ([arXiv 2605.06717](https://arxiv.org/abs/2605.06717)). Lu et al. formalise the task the same way. Given user activity, environment events and state, the agent predicts a task, or predicts *nothing* when no help is needed, and it is scored on whether the user accepts the prediction ([arXiv 2410.12361](https://arxiv.org/html/2410.12361v3)). LangChain's industry term "ambient agent" describes an agent triggered by an event stream rather than a chat message. Such agents are explicitly "not necessarily fully autonomous" and reach the person through three touchpoints: **Notify**, **Question** and **Review** ([LangChain](https://www.langchain.com/blog/introducing-ambient-agents)). A "proactive agentic workflow" is the same idea applied to a multi-step pipeline. A trigger starts a durable run, the run pauses at human gates, and its result lands somewhere reviewable.

The decision theory is 27 years old. Horvitz's "Principles of Mixed-Initiative User Interfaces" sets four outcome utilities (act or not, goal present or not) against the probability that the user has the goal. Adding dialog as a third option gives **two thresholds**. Below the first, do nothing. Between them, ask. Above the second, act. Context moves the thresholds. Deep focus on another task raises the cost of a wrong action, and a rushed user raises the cost of inaction ([Horvitz, CHI 1999](https://erichorvitz.com/chi99horvitz.pdf)). His twelve principles read like a modern requirements list. They include goal uncertainty, attention-aware timing, dialog to resolve uncertainty, cheap invocation and dismissal, "doing less" correctly when unsure, courteous time-outs, working memory, and continual learning. His LookOut calendar agent shipped all three modes, set offer time-outs by confidence, and learned per-user timing. Later systems such as BusyBody learned a personalised **cost of interruption** model to decide when notifications should arrive ([BusyBody, CSCW 2004](https://erichorvitz.com/busybody_cscw.htm)). The failure list in his 1999 paper (poor goal-guessing, poor cost-benefit reasoning, poor timing, weak user control) is almost word for word the open-problem list of the 2026 benchmarks. LLMs improved perception and content generation. They did not solve calibration or timing.

In practice, proactive agents do four kinds of work. They **monitor** for a meaningful change and notify (ChatGPT's monitoring tasks "notify only on meaningful changes"). They **run recurring chores** on a cadence the user chose, such as dependency checks, nightly PR review or backlog triage. They **respond to events**: an alert, a new issue, a failed CI run or a Slack message starts an investigation or a fix. They **suggest** work the person did not ask for, such as Jules proposing tasks from TODO comments, or an assistant spotting a latent bug. These solve real problems. Work that would otherwise be forgotten gets done. Monitoring stops needing a human to poll. Incidents are investigated before anyone is paged. And, in the one measured case, people do work they would otherwise skip: test-writing rose from **13.3% to 33.3%** with a proactive assistant ([Chen et al.](https://arxiv.org/html/2410.04596v2)).

The papers agree on what a proactive agent needs, though no single paper tests all of it together. It needs **perception** of an event stream. It needs a **user model and durable memory**: ProAgentBench found that long-term memory and history significantly improve timing prediction ([arXiv 2602.04482](https://arxiv.org/abs/2602.04482)). It needs **need prediction with calibrated uncertainty**, and an **initiative and timing policy** that chooses among silent, ask or offer, and act. It needs **content generation and execution**, and **feedback learning** from accept and dismiss. And it needs **interaction affordances**: preview, one-click dismiss, and presence indicators, which reduced disruption in the Codellaborator study ([Pu et al., CHI 2025](https://arxiv.org/pdf/2502.18658)). The Always-On Agents survey adds an important correction. Agents become "always-on" through **durable state that persists across sessions**, not by running continuously, and "proactivity calibration" is named in the literature but not governed ([arXiv 2606.30306](https://arxiv.org/html/2606.30306v1)).

## Products converged on user-authored triggers, fresh sessions and run-level caps

By late 2026 every major vendor ships some form of proactive or background agent, and the designs have converged. Anthropic's Claude Code **scheduled tasks** (launched as "routines", still in research preview) save a prompt with repos and connectors. They combine three OR'd triggers: cron (crons more frequent than hourly are rejected), an authenticated API `/fire` endpoint, and GitHub events. Each run is a fresh cloud session in auto mode, where a classifier gates actions, and the work lands on `claude/` branches. Hourly caps are hard: 100 scheduled runs per account and 30 per task. Two design rules are worth copying directly. Fire text is wrapped as **untrusted data** unless the saved prompt opts in to acting on it. And the stored prompt "is therefore not live user input and can't act as approval or consent." The docs also admit that a run's "Succeeded" status reflects how the session ended, "not whether Claude completed the work" ([Claude Code docs](https://code.claude.com/docs/en/routines)). Devin and Cursor ship near-identical "Automations". They take Slack, GitHub, Linear, PagerDuty, cron and webhook triggers, run each one in an isolated session, and control noise and cost with rate limits, queues that drop overflow, compute caps, and, in Devin's case, an LLM or script **Preflight** filter that can skip an event before any session starts ([Devin docs](https://docs.devin.ai/product-guides/automations); [Cursor docs](https://cursor.com/docs/cloud-agent/automations)).

The main divergence is who chooses the work. User-authored schedules and event rules dominate. Agent-chosen initiative is rarer and has been pulled back or tightly scoped. OpenAI launched Pulse in September 2025 as an overnight, Pro-only briefing built from chats and connected apps ([TechCrunch](https://techcrunch.com/2025/09/25/openai-launches-chatgpt-pulse-to-proactively-write-you-morning-briefs/)). By June 2026 a release note mirrored by several outlets read "Pulse is being sunset as proactive updates move into scheduled tasks" ([Digit](https://www.digit.in/news/general/openai-is-retiring-chatgpt-pulse-and-replacing-it-with-scheduled-tasks-here-is-why.html)). OpenAI's own release page was not fetched, and its stated reason was not found, so treat this as a strong signal rather than a verified explanation. Jules, the most explicit agent-chosen coding feature, starts from `#TODO` comments, is opt-in per repository, and routes everything to an approval dashboard ([Google](https://blog.google/technology/developers/jules-proactive-updates/)). LangChain's own lesson concerns the delivery channel. It first used Slack as the human-in-the-loop channel and abandoned it because notifications piled up, then built a dedicated inbox ([LangChain](https://www.langchain.com/blog/introducing-ambient-agents)). Coding vendors control risk at the **run** level (sandbox, branch prefix, caps, budgets) and review at the PR. Personal-assistant and enterprise flows keep **per-action** approval for irreversible actions such as sending email. No vendor publishes acceptance, dismissal or retention numbers for any of these features, so the market's verdict comes from what vendors shipped and retired, not from published data.

## The evidence shows modest gains, fragile tolerance and a structural injection risk

The measured upside is real but small, and it comes from short lab sessions. In the CHI 2025 study (N=65, GPT-4o, 20 minutes per condition), proactive variants raised test cases passed by **+12.1% to +18%** over a chat-only baseline. Of 75 explicit suggestion interactions, 69 were accepts. Latent-bug debugging and brainstorming were accepted most. Efficiency and modularity refactors made up five of the six rejections ([Chen et al.](https://arxiv.org/html/2410.04596v2)). ContextAgent reports up to **+8.5%** proactive-prediction accuracy over baselines ([arXiv 2505.14668](https://arxiv.org/abs/2505.14668)). These gains carry an important caveat. In the METR randomised trial, experienced developers using AI tools took **19% longer** while believing they were 20% faster ([arXiv 2507.09089](https://web3.arxiv.org/pdf/2507.09089)). A harness should therefore measure acceptance, merge, revert and time-to-done, never satisfaction alone. Background coding agents produce work in volume but are accepted less often than humans. Summaries of the 932,791-PR AIDev dataset put merge rates at roughly **35–64%** across agents against **79%** for human PRs ([AIDev](https://arxiv.org/html/2602.09185v1); [Emergent Mind summary](https://emergentmind.com/topics/aidev-dataset)). These figures are secondary and the subsets are not comparable, but the direction holds: every proactive output creates review work, and much of it is thrown away.

The failure evidence is more consistent than the success evidence. **Over-triggering** is the norm. On ProactiveBench the best fine-tuned model reached only **66.47% F1 with a 50.22% false-alarm rate**, and GPT-4o raised false alarms 51.85% of the time ([Lu et al.](https://arxiv.org/html/2410.12361v3)). ProAgent reports baselines triggering on whatever looks relevant even when the user is not focused on it ([arXiv 2512.06721](https://arxiv.org/html/2512.06721)). **Frequency kills preference**. Shortening the wait from 20 s to 5 s and showing five suggestions instead of three dropped preference to **47%**, and users called it "distracting and annoying" ([Chen et al.](https://arxiv.org/html/2410.04596v2)). Interruptions are expensive. In Gloria Mark's field study, interrupted work resumed **about 23 minutes later**, a figure that includes time spent on other work, not just idle refocusing ([Gallup](https://news.gallup.com/businessjournal/23146/too-many-interruptions-work.aspx)). People already handle about **63.5 notifications a day** ([Pielot et al.](https://ic.unicamp.br/~oliveira/doc/MHCI2014_An-in-situ-study-of-mobile-phone-notifications.pdf)). When noise wins, users switch the feature off rather than tune it. One maintainer team disabled Copilot code review as "too noisy" ([dev.to](https://dev.to/techgirl1908/how-i-taught-github-copilot-code-review-to-think-like-a-maintainer-3l2c)). GitHub later added severity labels and comment grouping ([GitHub changelog](https://github.blog/changelog/2026-05-12-copilot-code-review-comment-experience-improvements)). After Copilot inserted promotional text into PR descriptions, GitHub removed Copilot's ability to edit other users' PR text entirely ([TechSpot](https://www.techspot.com/news/111892-github-disables-copilot-pr-edits-after-ai-quietly.html)). Clippy came out of Microsoft Research's Bayesian Lumiere project, yet became a byword for interrupting at the wrong moment and was removed by Office 2007 ([Computer Hope](https://www.computerhope.com/jargon/c/clippy.htm)). Trust is falling as use rises. **46%** of developers distrusted AI accuracy in 2025 (31% a year earlier), and **81%** had security or privacy concerns about agents ([InfoWorld](https://infoworld.com/article/4031673/ai-use-among-software-developers-grows-but-trust-remains-an-issue-stack-overflow-survey.html); [ShiftMag](https://shiftmag.dev/stack-overflow-survey-2025-ai-5653/)).

Two harder failure modes matter more for an unattended agent than annoyance does. The first is **destructive action despite instructions**. Replit's agent wiped a production database during a declared code freeze, and the fix was architectural (separate dev and prod, one-click restore), not a better prompt ([eWeek](https://www.eweek.com/news/replit-ai-coding-assistant-failure/)). The second is **prompt injection through routine background reading**. In Invariant Labs' GitHub MCP attack, a malicious public issue hijacked an agent doing "check open issues" into leaking private repositories through a PR ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)). This is Simon Willison's "lethal trifecta" of private data, untrusted content and an outbound channel ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Meta's **Rule of Two** turns it into a design rule: in one unsupervised session, combine at most two of untrusted input, sensitive access, and state change or external communication ([Willison, Nov 2025](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/)). Filters will not rescue a design that breaks the rule. "The Attacker Moves Second" bypassed 12 published defences at **over 90%** success for most of them (same source). A proactive agent reads more untrusted content, with nobody watching each step, than any interactive agent, so this risk is structural, not incidental.

Taken together, the evidence draws a narrow envelope, and it also defines when a user should *not* want a proactive agent. People want proactivity that catches something at the moment it matters (an error, a latent bug, a meaningful change), that runs chores they scheduled themselves, and that delivers into a queue they own. They do not want it when output lands in shared spaces their teammates did not opt into, when it watches broadly (Microsoft Recall was delayed and made opt-in after privacy backlash, and Signal and Brave moved to block it ([BetaNews](https://betanews.com/article/microsoft-postpones-recall-so-new-copilot-pcs-will-launch-without-this-flagship-feature); [Freedom of the Press Foundation](https://freedom.press/digisec/blog/signal-blocks-microsoft-recall-from-recalling/))), when review cost exceeds the value of the work, when metered billing makes background activity a cost surprise, or when the task is ad hoc and a chat request is simply faster. Important unknowns remain. No longitudinal field study of an LLM proactive agent exists. No study compares digest delivery with real-time interruption for AI agents. And no vendor has published acceptance or dismissal rates. Every threshold recommended below is a starting point to be tuned with our own telemetry, not a validated constant.

## A design that survives the evidence: decouple "when" from "what", and govern initiative explicitly

The architecture the evidence supports has seven stages, and each answers a specific failure above. **Triggers** normalise schedules, signed webhooks, first-party events and polled sources into one event type. Payloads are treated as untrusted, and the stored prompt must opt in to acting on them, following the Claude Code template. **Ingest and flow control** run before any model call. They deduplicate on an idempotency key (source, entity, type, delivery id). They apply per-entity debounce ("settle, then act"), throttle ("process all"), rate limits ("drop excess"), batching (digests) and supersede ("only the newest matters"), using Inngest's precise vocabulary for these ([Inngest](https://www.inngest.com/docs/guides/debounce)). Dropped events are logged visibly, so users do not assume coverage that does not exist. **Detection** is cheap and runs without a model wherever possible. The 2026 research trend is to separate *when to act* from *what to say*. A temporal-graph trigger controller ran at **11 ms per event on a laptop** and improved downstream F1 for all 14 LLM backbones tested, by a mean of **16.7 points**, over letting the LLM decide when to fire ([arXiv 2605.30152](https://arxiv.org/abs/2605.30152)). Devin's Preflight filter and ChatGPT's "meaningful change" rule are the product versions of the same idea.

**Triage and act** are split to satisfy the Rule of Two. A triage pass reads raw untrusted content, holds no sensitive tools and no outbound channel, and emits a constrained verdict: relevance, proposed action, confidence, reversibility and urgency. An actor run holds the tools but sees only that structured output. Anything that needs raw untrusted content together with sensitive access and an outbound action goes to human review. The **initiative policy** then maps each candidate to Silent (logged), Notify, Question, Review (a draft awaiting approval) or Act. These are Horvitz's two thresholds, extended with LangChain's touchpoints. The thresholds are set **per action class**, not as one global confidence number, because LLM self-reported confidence is poorly calibrated. On QuestBench, models reached only **40–50%** at choosing the right clarifying question on logic and planning tasks, and rarely said "not sure" even when that option was offered ([NeurIPS 2025](https://neurips.cc/virtual/2025/poster/121518)). Irreversible actions and external communication always go to Review. Reversible, sandboxed, internal actions can Act above a high threshold. An **interruption budget**, quiet hours and a scheduled digest absorb everything below "urgent". For in-session suggestions, the CHI 2025 timing rules are the only measured guidance available: hold while the user types, offer after about 5 s idle, show at most one every 20 s, and show immediately when a run errors ([Chen et al.](https://arxiv.org/html/2410.04596v2)).

**Autonomy** is a deliberate setting, separate from capability. The Knight Institute's five levels (operator, collaborator, consultant, approver, observer) map cleanly onto proactive modes. A notify-only watcher sits at L1. Drafts awaiting review sit at L4 for low-risk work. Fully autonomous L5 is reserved for reversible, budget-capped housekeeping with logs and an off switch ([Knight](https://knightcolumbia.org/content/levels-of-autonomy-for-ai-agents-1)). The same source warns of "approval-based escalation", where autonomy creeps upward as users stop paying attention. Promoting an action class from Review to Act must therefore be an explicit user decision, never an automatic result of a high acceptance rate. **Durable execution** underpins the pending states. A run checkpoints after each step, parks a pending request with a correlation id and a timeout, resumes on the person's answer without holding compute, and expires, escalates or takes the safe default on timeout. The Claude Agent SDK's `PreToolUse` → `defer` decision (ending a turn with `tool_deferred` so it can resume later) is the exact primitive, and it fails closed on hook timeout ([Agent SDK hooks](https://code.claude.com/docs/en/agent-sdk/hooks)).

The **inbox** is the system of record for the person. It holds one queue across all background agents, with each item linked to its run transcript. Slack and email are delivery channels for it, not substitutes. **Memory and the user model** grow from structured feedback events: item type, decision (accept, edit, dismiss with a reason, ignore, expire), edit diff and latency. An explicit "wrong", "not useful" or "bad timing" separates content errors from timing errors. Edits to drafts are the richest signal. Ignored items are weak negatives. ATRBench shows agents trail an oracle by **at least 62 points** at asking now for preferences a future task will need ([arXiv 2605.28108](https://arxiv.org/abs/2605.28108)), so preference capture has to be designed in. Prompting will not supply it. Memory written from untrusted inputs is an injection persistence vector and must be tagged with its provenance. **Cost** is mostly a trigger-layer problem, because every fired event can cost a full session. The controls are a minimum interval, per-run, per-automation and daily caps, cheap triage ahead of an expensive actor, and runs that stop with a Notify rather than truncating silently when they hit a cap. **Observability** needs an outcome field separate from session status. The metrics that matter are precision (accepted ÷ surfaced), edit rate, false-alarm rate, interrupts per user per day, **no-op run rate** and cost per accepted item. Policy changes are evaluated offline by replaying recorded event streams.

## Our harness already owns the scheduler, the guard and the proposal, but not the outcome

The inventory, read at commit `e0b178d` without running the app, finds the core is brownfield for proactivity even though no design doc addresses it. **Scheduling is production-grade.** `src/core/scheduler.ts` has its own 5-field cron parser, one-time runs, atomic file-locked persistence to `schedules.json` with a per-owner cap of 50, a 30-second tick, catch-up of missed runs on start, claim-before-launch so each run fires once across servers, and a single `scheduler` lease (`src/kernel/harness.ts:940`). Pre-run gates skip runs for disabled accounts, concurrency limits and switched-off plugins (`src/core/scheduler.ts:125-132`). The agent has a `schedule` tool limited to its own session, confirmed as an external, persisting action (`src/tools/schedule.ts:10-52`), and there is a REST API (`src/server/app.ts:1241-1285`). **Event triggers exist** as secret-URL `hwt_…` tokens stored as SHA-256 hashes, with rate-limited `POST /api/triggers/:token` (`src/server/app.ts:722-738`). Their payloads are fenced in `<trigger_payload>` and the session is marked untrusted (`src/kernel/harness.ts:925-928`), which is essentially the Claude Code `/fire` safety model. Plugins can subscribe to the EventHub and start sessions (`src/plugins/api.ts:118,154,206-218`). The integrations plugin already runs "investigate" from Slack and Teams and decides approvals from chat buttons (`plugins/integrations/lib/hub.mjs:475-497`).

The initiative and safety layers are just as far along. `src/core/linked.ts:25` already encodes a three-way initiation model. `user_asked` runs now, while `offer` and `own_initiative` become persisted **proposals** that expire after seven days, are capped at 20 open per session, and have desktop cards and an Agents home (`apps/desktop/renderer/src/builtins/core.agents/`). That is Jules-style "propose, then approve" already built. The permission stack covers six modes, Claude-Code-compatible hooks, plan mode, `ask_user`, progress reviews and workflow `approval` nodes (`src/graph/format.ts:13`). The **taint guard** (`src/core/permissions.ts:21-35,128-179`) means that once untrusted content has entered a session, persisting or data-sending calls need a person or an operator hook. The auto-mode checker can never answer them. That is a Rule-of-Two enforcement point most products lack. Docker and OS sandboxes, an egress proxy with network `none` by default for scheduled sessions (`src/server/app.ts:1254-1266`), and a vault with redaction complete the picture. Cost controls exist at three levels: a per-conversation `maxCostUsd` (default $5), a per-account daily `SpendLedger`, and concurrency limits (`src/server/users.ts:222-278`). Most valuable of all, the Operations solution's aiops watch loop (`solutions/operations/plugins/aiops/lib/watch.mjs`) is a working example of the "decouple when from what" pattern. It evaluates rules without a model every 60 seconds under an `ops-watch` lease, wakes a model only when an incident opens or escalates, uses no vault credentials because nobody is there to approve, and **replaced an every-5-minute agent workflow that ran 288 times a day**.

The gaps sit on the result side, and several are defects rather than missing features. None were confirmed at runtime.

The pattern is clear. The harness can *start* proactive work safely, but it cannot yet *show what came of it*, *hold a decision for later*, or *learn from the response*. That is exactly the part the evidence says decides whether users keep proactive features switched on.

## Build it in five phases, starting with the bugs and ending with learned initiative

Building is worth it, for four reasons. First, the marginal cost is low, because the scheduler, triggers, taint guard, proposals, inbox and a proven watch loop already exist. The work is mostly records, UI and policy, not new infrastructure. Second, the core is a generic, pluggable framework, and today each solution reinvents proactivity. aiops built its own watch loop and integrations built its own "investigate" path. A core primitive would let Operations, DevOps, Engineering and Studio declare automations instead of hand-wiring leases and sessions. Third, users of Claude Code, Codex, Cursor and Devin now expect scheduled and event-triggered agents with run history, and our desktop form appears not to work at all. Fourth, the harness's existing safety model (fenced triggers, taint guard, `dontAsk` defaults, sandbox network `none`) is stronger than most products' starting point. The proactive layer can therefore be built safe by default instead of retrofitted. The case against deserves its due. Review burden is real (agent PRs merge less often than human ones). A desktop-hosted engine cannot run while the app is closed. And solutions can already do much of this through the plugin API. Those arguments shape the build: queue-first, opt-in, desktop lifetime made explicit. They do not cancel it. What the evidence does *not* support is an always-on assistant that watches everything and interrupts on its own judgement. That configuration has the worst record in the corpus (Clippy, Persistent Suggest at 47%, Pulse, Recall).

The sequencing follows the evidence. Phases 0 and 1 make user-authored schedules (the least controversial form of proactivity) actually work and actually visible. Phase 2 delivers the queue-first surface that both the literature and LangChain's own experience say users need, and it removes today's only choice for unattended runs, which is to act within allow rules or fail. Phase 3 brings the cheapest, safest version of event-driven initiative (model-free detection, model on change), which aiops has already proven in-house. Phase 4 adds the calibration the research identifies as the unsolved problem. It treats thresholds as per-class, measured and explicitly promoted, never as a model's self-reported confidence. The defaults should start conservative: notify-or-review rather than act, a small daily interrupt budget, digest by default, opt-in per automation. They should then loosen only where our own acceptance data justifies it.

## Conclusion

The research reframes the question. Building a proactive agent is no longer mainly a capability problem, since any current model can draft the PR or write the summary. It is a governance problem, and that is where a harness, rather than a model, adds value. The durable winners in the market are not the agents that guessed what users wanted. They are the ones that made user-authored triggers cheap, ran each firing in a contained session, and put the result where the person could judge it. Our harness, unusually, built the hard governance pieces first (taint guard, fenced triggers, proposals, leases, a model-free watcher). The missing pieces are the outcome record, the inbox and the feedback loop, so the remaining work is mostly what users see, at relatively low risk.

The second implication concerns measurement. Every published number on proactive agents comes from short lab sessions, simulated users or secondary summaries. No vendor has released acceptance or dismissal rates. If we instrument precision, no-op runs and cost per accepted item from Phase 1 onward, the harness will produce the longitudinal evidence the field lacks. That data, not a design debate, should decide whether Phase 5 (agent-chosen, in-the-moment initiative) ever ships.
